# Story 2.3: Retry, failure recovery and resumable execution

Status: review

## Story

As a sponsor operator,
I want failed or timed-out submissions handled safely,
so that a close never double-submits, never leaves me guessing what happened, and can be resumed after a crash.

## Acceptance Criteria

As written in `docs/epics-and-stories.md` (Story 2.3). Three of them are met in another form than their wording; each is marked as a documented deviation, with the reason.

1. AC-E2-S3-1: Given Horizon returns a 504 timeout for a transaction that was actually included, when recovery runs, then the executor finds the transaction by hash, marks it confirmed and does not resubmit (mock test).
2. AC-E2-S3-2: Given `tx_bad_seq`, then the transaction is rebuilt with a fresh sequence number and resubmitted once; a second `tx_bad_seq` aborts with `SequenceConflictError`.
   - **Documented deviation.** Nothing is thrown: a second `tx_bad_seq` ends the run with the returned report, `status: "failed"` and `stop.code: "SEQUENCE_CONFLICT"` (verdict `replan`, with the refused envelope's hash and result codes). Reason: ADR-0006, "Plans and reports never throw for expected conditions". A sequence clash is an expected condition, and a returned report keeps every hash already submitted (PRD NFR-03). Exceptions are kept for the unexpected, and they carry the report too (review finding R1).
   - **Documented deviation (the re-plan branch).** The transaction is not always rebuilt with a fresh sequence number. When `tx_bad_seq` meets a transaction one of whose earlier envelopes was never seen on the ledger (it ended `unknown`), or when Horizon cannot find an envelope by hash while the account shows its sequence number used (edge case E5), nothing is rebuilt: the rest of the close is re-planned from the ledger instead, and the report gains a `replans[]` entry. Reason: ADR-0006's `TX_BAD_SEQ` row ("poll by hash; if applied, continue; else replan"). The unseen envelope may have applied, and sending its operations again at a new sequence number could apply them twice; the re-plan plans only what the ledger still shows. The refusal proves the number used, and the unseen envelope's entry records it (`sequenceUsed`, review round 3, R3-11).
3. AC-E2-S3-3: Given `tx_insufficient_fee`, then the outer fee bid is raised stepwise up to the cap, then aborts with `FeeCapExceededError`.
   - **Documented deviation.** Nothing is thrown: when neither the per-operation cap nor the close budget allows a higher bid, the run ends with the returned report, `status: "failed"` and `stop.code: "FEE_LIMIT"`, with a message naming the limit that was reached. Reason: ADR-0006, as for AC-2.
4. AC-E2-S3-4: Given an operation failure code, then the receipt records the step, the code and a human explanation, execution re-plans from live state, and a step that fails twice is reported as a blocker and execution stops before the merge.
   - **Narrowed for the merge by E3-S4 (2026-09-28).** `op_seq_num_too_far` is no longer a plain stop: the executor reads the account again, waits for the sequence guard within the plan's `maxWaitLedgers` and rebuilds the merge. A merge that fails that way twice stops with `SEQNUM_TOO_FAR` and the ledger to come back at, and is not added to `report.blockers` as `STEP_FAILED_TWICE`; the stop and the receipt's "Next" line report it (docs/stories/3-4-seqnum-too-far-guard.md). Only failures with `op_seq_num_too_far` count toward that twice, and a merge with no re-plan or budget left after such a failure stops the same way, with the ledger (closing review CX-4, CX-5). Every other step that fails twice is still a `STEP_FAILED_TWICE` blocker.
5. AC-E2-S3-5: Given a crash after transaction 1 of 3, when the close is rerun for the same account, then the executor re-plans, skips work already done and completes (unit test with recorded state).
6. AC-E2-S3-6: Then every submission attempt is appended to `receipt.json` as it happens, not only at the end.
   - **Documented deviation.** The SDK writes no file: every change of the report is published as a copy through `ExecuteOptions.onReport`, and the CLI writes that copy to the file named by `--report <file>`, through a temporary file and a rename so that no reader sees half a file. There is no `receipt.json`. Reason: the PRD gives the file to the CLI (FR-17, "The Close Report is written incrementally by the CLI (`--report <path>`)"; FR-18, "`executeClose()` returns, and `dustin close` writes, a Close Report"); an SDK caller keeps the copies wherever it keeps its own state.

## Dev Notes

- Policy: canonical decision 7 (fees, rebuild after `tx_too_late`, never 10x replace-by-fee), architecture sections 4.6, 4.7 and 7, ADR-0006 (verdicts), PRD FR-12, FR-15, FR-17, NFR-02, NFR-03, NFR-11.
- Safety of rebuilds. An envelope is replaced only when it can never apply: refused with `tx_too_late`, or not found by hash after its time bound passed. Time bounds are judged by ledger close time (https://developers.stellar.org/docs/learn/fundamentals/transactions/operations-and-transactions#time-bounds): the confirm loop reads the latest close time once, asks again only when that reading plus the time waited says the bound has probably passed, and uses the local clock only to measure the wait (review finding 6). A last lookup after a ledger closed past `maxTime` decides; if no such ledger appears within `ledgerWaitSeconds` (default 60), the run stops with `OUTCOME_UNKNOWN`, and the stop names the envelope's hash and `maxTime` so a re-run can wait for a ledger past it (review finding 7). A replacement for a still-queued envelope would need a 10x bid (https://developers.stellar.org/docs/build/guides/transactions/fee-bump-transactions#replace-by-fee), which Dustin never relies on. An envelope refused for its fee was never queued; envelopes for one sequence number can apply at most once between them.
- Lookups by hash have three results: found, missing (404) and error (429, 5xx, timeout, unreadable body). An error proves nothing, so it is only tried again within the same bound and then stops the run with `OUTCOME_UNKNOWN`; a submitter without `lookup()` is read the same way (review finding 1). A lookup that throws is an error too (review round 3, R3-16), and so is a failed read of the latest ledger or of the account inside the wait, or a close time that is not a number: the envelope then ends `unknown` with `readError`, and the entry records the cause in `lookupError` (R3-14, R3-17, R3-22). Failures get the grace and the ledger wait from the first of them (R3-21), and the whole wait for one envelope is bounded on the local clock by `timeoutSeconds` plus twice the grace and the ledger wait, whatever Horizon answers (R3-17; blind review BH-4). Since the closing review every pause of these waits is `pollIntervalMs` clipped to the time left, never below 200 ms, so one long pause cannot outlast the bound; a clock that gives no time leaves the pause whole (`clipPause` in `src/config/pauses.ts`, CX-8).
- A 404 is trusted only when the account does not contradict it (edge case E5). A 404 by hash carries no ledger: SDF testnet Horizon sent no `Latest-Ledger` header on `GET /transactions/{hash}` (observed 2026-09-27), and Horizon's own replica check (`ReplicaSyncCheckMiddleware`, https://github.com/stellar/stellar-horizon/blob/main/internal/httpx/middleware.go, commit 5519313; installed by `router.go` only with a primary database, commit f043341) covers a read replica of one deployment, answering 503. So once a ledger has closed past the bound, a 404 counts only while the account shows the envelope's sequence number unused (a missing account counts as used); otherwise the attempt re-plans from the ledger and never rebuilds. Before the final check every envelope still `unknown` is looked up once more. Whether the testnet address serves instances that lag each other is not verified; the check costs one account read. The same witness settles a 400 that `settleInclusion` looks up (edge case E6) and finds missing: an answer that reads as an included failure (inner `tx_failed`, or an inner `tx_too_late` at apply time) stays included while the account shows the number used or cannot be read (review round 3, R3-8).
- An account read below a sequence number that this run's own included transactions used comes from a Horizon behind the one that took them: the attempt loop and the merge preflight read it again after `pollIntervalMs`, at most five times, then use the last read (edge cases E3, E4). As above, such lag on testnet is not verified; the wait costs seconds, and acting on the stale read would build at a used sequence number or refuse a clean merge. Since round 3 a mid-run re-plan reads the account the same way, and a number counts as used also when Horizon did not find an envelope whose number the account showed used, and when a `tx_bad_seq` refusal proved it (R3-11). The envelope's explanation then names that refusal instead of an account read that showed the number unused (closing review CX-11).
- A 400 answering `tx_failed`, or for a fee bump `tx_fee_bump_inner_failed` with any inner code, does not say whether the transaction was included (edge case E6): stellar-core answers `txFAILED` when an operation fails its checks at validation, before any inclusion (https://github.com/stellar/stellar-core/blob/master/src/transactions/TransactionFrame.cpp, commit bb32c8a: `op->checkValid` failing, or operation signatures failing, set `txFAILED`), and an included fee bump can fail its inner transaction with another code. The hash is looked up: a record means included (sequence number used, fee charged), a 404 means refused at validation. Scripted included failures in the tests are recorded on the fake ledger for this reason (`recordIncludedFaults` in `test/unit/execute/harness.ts`).
- Budget. An inner sequence number is consumed once at apply time (https://developers.stellar.org/docs/build/guides/transactions/fee-bump-transactions#application), so at most one of the envelopes signed for it is charged. `FeeSponsor` therefore counts the largest bid per sequence number, not the sum of every signature, and a rebuild with a doubled bid costs only the difference; `headroomStroops()` lets the executor stop before signing when neither the cap nor the budget allows the next bid. A bid counts from before the signer is awaited and is taken back if the signer throws, so overlapping `wrap()` calls cannot both fit (blind review BH16; the executor calls it one at a time). Bids for a sequence number that another transaction consumed while every envelope for it was refused are released before the rebuild (`release()`, edge case E7): only the bids of this transaction's own refused envelopes, so a bid another transaction of the run holds for the same number (the charged one, when this transaction was built on a stale read) stays counted (`release(feeBumps)`, review round 3, R3-6). A re-plan's bids must fit `remainingStroops` before anything more is signed, or the run stops with `OVER_BUDGET` (review finding 5).
- `tx_bad_seq`: the instruction for this story (look the previous envelopes up by hash, then re-read the sequence and rebuild once) is followed; ADR-0006's row says "else replan", which is what happens when an earlier envelope stays unseen. A rebuilt transaction that meets a changed state fails on the ledger and re-plans through the operation path anyway. An inner `tx_no_source_account` (the account is gone) also looks the earlier envelopes up, since one may have been the merge, and otherwise stops with `ACCOUNT_MISSING`; an outer one names the sponsor and stops (review findings 2, 8; Horizon's string for `txNO_ACCOUNT` is `tx_no_source_account`).
- 429 is Horizon's per-IP rate limit (https://developers.stellar.org/docs/data/apis/horizon/api-reference/structure/rate-limiting): nothing was accepted, so the same envelope is posted again after `backoffMs`, doubled each time, at most `maxRateLimitRetries` (5) more times. A 400 without result codes or any other 4xx is refused at once and not polled (review finding R11).
- Result codes. `GET /transactions/{hash}` carries only `result_xdr`, so a transaction found failed after a 504 gets its codes rebuilt with the strings of stellar-horizon `internal/codes/main.go` (https://github.com/stellar/stellar-horizon/blob/main/internal/codes/main.go, commit 51fd177 of 2026-03-16). The decoder reproduces, from their `result_xdr` read on testnet Horizon, the codes Horizon returned at submission for four day-1 failures (`op_seq_num_too_far`, `op_no_issuer`, `op_src_not_authorized`, `op_invalid_limit`; hashes in `docs/progress-log.md` and `docs/research/day1-experiments-2026-09-26.json`), and a test checks that every member of the SDK's result enums for the operations Dustin submits is mapped. Horizon spells two codes differently from ADR-0006: `op_offer_not_found` (ADR: `op_not_found`) and `op_not_aut_maintain_liabilities` (ADR: `op_not_auth_maintain_liabilities`); the code matches Horizon.
- Ladder fallback without touching the planner. A mid-run re-plan reads through `withPathsOnlyFor()`, which offers strict-send paths only to the assets the approved plan sold on rung 1 and whose sale has not failed. A failed sale therefore falls down the ladder (canonical decision 8), and no asset moves up to rung 1 because a market appeared mid-run. The re-planned step's reason then says Horizon found no path; the report's `replans[].demoted` and the step outcome's `explanation` give the real reason.
- Drift during the run. `replanDrift()` compares the re-plan with the approved plan (round 0) by step identity (kind plus offer id, asset, data name or pool): a re-plan may drop steps that applied and move an asset down the ladder or off it; a step the approved plan did not have, a larger balance or a move up the ladder is drift and follows `onDrift` (default abort). A re-plan that can no longer merge stops with `PLAN_NOT_CLOSABLE` unless `allowPartial` is set; one that finds the account gone stops with `ACCOUNT_MISSING` and lets the final check decide (edge case E8).
- The merge preflight (`src/execute/preflight.ts`) runs before every merge-carrying transaction once anything was submitted in the run, and before every rebuild of one (edge case E2). Leftover subentries are checked only when the merge runs alone. Any sequence guard that is not ok blocks the merge, whether or not it names the unblocking ledger (blind review BH11).
- A failed merge preflight stops with verdict `replan` (run again) rather than re-planning inside the run: every preflight failure (a subentry, sponsorship, a missing or memo-required destination, the guard) ends in a blocker or in drift on the next plan anyway, and the run again shows it. Before a rebuild is refused this way, the unseen earlier envelopes are looked up, since the account may be gone because the merge applied.
- `op_seq_num_too_far` stays a stop with the unblocking ledger (`(seq + 1 >> 32) + 1`, canonical decision 10); waiting is E3-S4. (Superseded by E3-S4, see AC-4 above.)
- An included failure without an operation code, a fee bump included while its inner transaction failed before any operation ran (inner `tx_too_late` or `tx_bad_seq` at apply time), spent only a sequence number and a fee, so it re-plans like a re-plan code; its explanation says it was included. A failure whose result names no code at all still stops, with verdict `replan` (review round 3, R3-9).
- A stop raised by a re-plan carries the round of the transaction that forced it, next to its index and hash (R3-7). An `OUTCOME_UNKNOWN` stop whose envelope a later lookup (before the final check) finds applied or failed keeps its code and hash, loses `maxTime`, and its detail says what was found; another stop naming such an envelope gains a sentence (R3-35; blind review BH-11). The STEP_FAILED_TWICE remedy says what the user can do; `--partial` does not skip the step, since the next plan includes it again (R3-5; the `RunBlocker` comment says the same since CA-13). The run records the code of each failure of a step, so when the two failures had different codes the blocker and its stop name each in order (closing review CX-4).
- Observers. `onReport` and `onEvent` run inside `try/catch`: one that throws after something was signed cannot stop the run; its error becomes a warning, once per callback. An async observer whose promise rejects is caught the same way (review round 3, R3-15), and a warning from an `onEvent` that threw on "done" is published again (R3-20). When the promise rejects only after the run has finished, its warning is added and the report is published once more, so the last copy (the CLI's `--report` file) says what the returned report says (closing review CX-6). An applied transaction is published only after its steps and the merge are recorded (review finding 3). An envelope counts as posted (`attempts`) only when its POST starts, and the copy published as each POST starts counts it (R3-3).
- Numeric `ExecuteOptions` are checked before anything is read or signed, and an invalid one throws `CONFIG_INVALID` at stage `config` (edge case E11): counts are whole numbers (`maxAttemptsPerTransaction` at least 1, `timeoutSeconds` from 1 to 3600, `maxReplans` and `maxRateLimitRetries` at least 0, `budgetStroops` at least 1, `maxBaseFeeStroops` at least the 100-stroop minimum), bounds (`graceSeconds`, `ledgerWaitSeconds`, `verifyTimeoutMs`) are finite and not negative, and since the closing review at most 3600 seconds for the grace and the ledger wait and at most 3,600,000 ms (one hour) for `verifyTimeoutMs`, because they extend the waits for an unconfirmed envelope and for the final check (CX-9), and pauses (`pollIntervalMs`, `backoffMs`) are from 200 ms (builder decision D-5) to 2^31 - 1 ms, Node's timer limit, beyond which a timer fires at once; the doubled backoff after a 429 is capped at that limit too (review round 3, R3-18).
- Reserves returned to sponsors come from the removals that applied, in whichever round (edge case E9): each removed trustline, pool share and offer is credited to the sponsor its round's plan named; with the account verified gone after this run's merge, the sponsored signers and account entry are added from the plan that carried the merge, confirmed by hash or not. Since round 3, with the account verified gone after this run's merge, every sponsored entry that any round's plan named is credited (the account being gone proves each is gone, whoever removed it), and the steps an envelope that applied unseen carried are marked applied, with an explanation that they were not confirmed by hash (R3-12). Since the closing review that includes a step that failed in an earlier envelope which this one carried again; the step keeps its failure count (CX-10). An interrupted run computes them too (R3-13).
- Status semantics (canonical decision 5; `CloseStatus` in `src/execute/report.ts`).
  - `closed`: a merge of this run applied, seen by hash or proven by the account being gone after this run posted it. A verified close is `closed` with `verification.accountExists === false`; the CLI exits 0 only then.
  - Review round 3 (R3-1, R3-10): the proof by the account being gone counts only a posted merge envelope whose outcome is unknown (`unknown`, or `pending` mid-POST); one refused before inclusion or failed on the ledger cannot have removed the account, so the stop stands and the CLI exits 5. A merge seen applied is `closed` in every path, also when a lookup settles it only after a stop: when Horizon still returns the account at the final check, the report is `closed` with stop `ACCOUNT_STILL_EXISTS` and a message saying Horizon still returned the account, and the CLI exits 5. Until then `complete()` reported this state `failed` and `stopped()` kept its stale stop.
  - Closing review CX-1: an `unknown` merge envelope counts only while it may have applied: it may still apply (`mayStillApply`), its sequence number is known used (`sequenceUsed`), or its lookups failed (`lookupError`). One the run itself found gone past its time bound with its sequence number unused ("it can never apply", no flag) no longer proves a close: when someone else removes the account after it, the run keeps its stop (`failed`, CLI exit 5). `mayHaveApplied()` (`src/execute/report.ts`) states the rule once, for the executor's merge candidates and for the receipt's open merge (CC-10). The price, recorded in the `CloseStatus` comment: a merge that applied while a lagging account read showed its number unused, and whose record Horizon never returns, is reported `failed`; running the close again then finds the account gone (`ACCOUNT_MISSING`, nothing submitted).
  - `partial`: an `allowPartial` run did everything else. `aborted`: nothing was submitted. `failed`: stopped part-way; running again continues from the ledger.
  - `running`: only in the copies published while the run is in progress, never in a returned report or one carried by an error (blind review BH1).
  - Edge case E10, decided: `closed` keeps meaning "the merge applied". A merge that applied but could not be verified because the final check threw keeps `closed` with `verification: null`, a message saying it is unverified and `stop` holding the error, and the error is thrown carrying that report. The CLI tells it from a verified close (exit 5, not 0) and from a run that never submitted anything; changing the status would hide from an SDK caller that the merge, which cannot be undone, did apply.
  - A run that never saw its merge apply but finds the account gone after posting it (an envelope that may have applied, CX-1) is `closed` too: the merge envelopes are looked up once more, and if none is confirmed the message says so and `mergedXlm` stays null (review finding 2). Without a merge the final check is informative only: if it throws, the run keeps its real stop or its partial result and adds a warning (review finding 4).
- An `unknown` envelope carries `mayStillApply`: true while no ledger has closed past its time bound, false once it cannot apply any more; its `explanation` tells a failed lookup and a used sequence number from a plain 404 (blind review BH3). Since round 3 the entry also carries `lookupError` (why its outcome could not be settled) and `sequenceUsed` (its number is known used), which the receipt's label follows (R3-11, R3-22).

### Implementation Plan

- `executeClose()` validates (numeric options included), checks the submit endpoint (R6), re-plans (R12) and hands over to a `CloseRun`, which owns the report from then on. Expected outcomes return the report with `stop` set; exceptions finish it and are thrown carrying it (R1).
- `submitPlannedTransaction()` runs one planned transaction: read the sequence, check the bid against the cap and the budget headroom, build with Horizon-clock time bounds, sign, wrap, record the envelope, post (with 429 back-off), then apply the outcome rules above.
- On an included failure the orchestrator classifies the first failed operation, updates the step outcome, and either stops or re-plans through the path-limited reader, checks drift, closability and the remaining budget, records the re-plan and runs the new plan's transactions.
- The final check is `verifyClosed()`: it polls for the 404 only when a merge applied. Before it, envelopes still `unknown` are looked up once more.
