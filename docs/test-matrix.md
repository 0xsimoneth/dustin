Legend:

## How to run each tier (AC-E3-S6-1)

| Tier | Command | What it needs | Duration |
|---|---|---|---|
| Offline (unit) | `npm test` | Nothing. The network is blocked for the whole tier (`test/setup/no-network.ts`); the tests read recorded Horizon JSON (`test/fixtures/horizon/messy`, `pool-share`, `edge`, `edge-e4`, `reset`) or run on the fake ledger (`test/helpers/fake-ledger.ts`, `test/helpers/edge-ledger.ts`). | 113 files, 1057 tests on `0df4d09`: 15.2 s while the live tier ran at the same time (2026-09-28); the independent review of 2026-09-29 measured 14.8 s and 10.9 s, vitest's own figures, on two fresh clones of `e865bec` (`docs/reviews/2026-09-29-e4-review.md`, step 1) (the limit is 60 s) |
| Live (testnet), all files | `DUSTIN_TESTNET=1 npm run test:testnet` | Internet access to Friendbot and testnet Horizon. Every file builds its own throwaway accounts from Friendbot with fresh keys; nothing is shared between runs and the builder's baseline fixture is never touched. No key and no `.env` are needed. | about 5 minutes: 301 s locally on `0df4d09` (11 files, 58 tests), 321 s in CI on `d0d711c` (2026-09-28) |
| Live, one file | `DUSTIN_TESTNET=1 npx vitest run --project testnet test/testnet/edge.test.ts` | as above | about 185 s for `edge` (17 tests), 28 s for `literal-zero`, 252 s for `ladder` (2026-09-28) |

Options of the live tier:

- `DUSTIN_RECORD=1` re-records the offline vectors from the run's fresh fixture: `testnet/edge` writes `test/fixtures/horizon/edge-e4/` (the current recipe, thirteen variants; since E4-S3), `testnet/pool-share-removal` writes `test/fixtures/horizon/pool-share/`. Both refuse to write a file that contains a secret seed. `test/fixtures/horizon/edge/` keeps the recording of the ten-variant recipe of E3-S6, which the older offline tests read.
- `DUSTIN_EVIDENCE=1` makes `testnet/execute-close` write `evidence/runs/<UTC stamp>/`; with `DUSTIN_EVIDENCE_LABEL=e3` the directory is `<UTC stamp>-e3`, as for the metric close of E3-S7.
- `DUSTIN_LADDER_RECORD=<file>` (`testnet/ladder`), `DUSTIN_UNWIND_RECORD=<file>` (`testnet/sponsored-unwind`) and `DUSTIN_GUARD_RECORD=<file>` (`testnet/sequence-guard`) also write every transaction hash with its purpose to that file.
- The live tests print every transaction hash with its purpose. In a shell that vitest recognises as an AI agent it picks its `minimal` reporter, which hides the output of passing tests; add `--reporter=verbose` to see it.

The fixtures the live tests build can also be built by hand:

- `dustin fixture create --profile messy`: the metric account (SOW Appendix B).
- `dustin fixture create --profile edge`: one throwaway account per edge variant (table below).
- `dustin fixture verify <dir>/<id>/manifest.json`: re-checks either profile against Horizon (exit 0 when every check passes, 3 when one fails). Before any check it stops with `RESET_SUSPECTED` (also exit 3) when the testnet looks reset: none of the manifest accounts it reads exists, and either Horizon's latest ledger lies more than 120 ledgers (about ten minutes) below the one the manifest records, or Horizon holds no operation for any of them (row X-15). Any other account that answers 404 fails its "exists" check with the reason: closed by its merge (ledger and hash), gone, or never seen by Horizon. An edge manifest is checked for the variants it lists, so a fixture built before E4-S3 still verifies.
- `npm run evidence:check [-- <file.md> ...]`: checks every link and every listed transaction hash of the evidence package (AC-E4-S7-3; by default every Markdown file under `evidence/`, `README.md` and `docs/write-up.md`): relative links against `git ls-files` and anchors against the target's headings, every transaction hash (linked, or listed in a code span or a table) on testnet Horizon, accounts on testnet Horizon with their history (a merged account's 404 is "account gone", an account with no history fails), every other https link by its status; mainnet hosts and explorers are refused without a request. Exit 0, 1 when something failed, 3 when nothing failed but something could not be checked (network error, timeout, 429 or 5xx after the retries, a bot protection's 403), 2 for a usage error. About a minute; it needs the internet.

`fixture create` writes the keys to `.fixture/<id>/keys.json` (mode 600, gitignored, testnet only), and the public manifest and the recorded Horizon JSON beside them.

## Where the tests differ from the matrix text

These follow the canonical decisions in `docs/README.md` and the PRD's decisions after review, which override the matrix where they disagree.

- **Codes.** The code uses `THRESHOLD_UNMET` (matrix and Story 3.5: `RAISED_THRESHOLDS`), `AUTH_IMMUTABLE_SET` (Story 3.5: `AUTH_IMMUTABLE`) and `LIQUIDITY_POOL_SHARES` (architecture 5.3: `LP_SHARES_HELD`), as PRD section 7 lists them (decision D-2: the SDK keeps the names it was built with).
- **S-02, X-04: steps next to a blocker.** The matrix asks for no teardown steps while a merge blocker holds. The planner lists every safe cleanup step with the blocker (architecture 4.3), and the executor refuses to run any of them unless `allowPartial` (`--partial`) is set (canonical decision 4), so nothing is signed by default. The X-04 variant has no subentry, so its plan has no step at all.
- **S-08: plan status.** The planner marks held pool shares as a blocker, so the plan is `blocked`; PRD FR-08 expects `partial`. The test `plan/review-e1` › treats liquidity pool shares as a merge blocker, so the plan is blocked pins the current behaviour.
- **AC-E3-S6-3, the forced payment.** Accepted by the builder on 2026-09-28 (decision D-8), and the criterion was rewritten to it. The planner never plans a payment it knows will fail, so no run submits one for the frozen FRZ. The payment is forced twice: as a negative probe outside any plan (`op_src_not_authorized`), and on the auth-revoke variant, whose trustline the issuer revokes after planning, so the executor's planned return fails with `op_src_not_authorized`, is recorded on the transaction, the step and the re-plan, and `allowPartial` runs the rest.
- **Fixture profiles.** Story 3.6 names the profiles `authreq`, `clawback`, `lp` and `multisig`, and PRD FR-21 a `--variant` flag. Canonical decision 3 defines two profiles, so the edge cases are variants of the one `edge` profile (`dustin fixture create --profile edge`), one account each.
- **S-04: the bump and the bound.** The matrix text bumps the sequence number 240 ledgers ahead and names a `--max-wait` flag. The live tests bump it 16 ledgers (the executor waits, then merges), 720 (the plan is blocked) and 10 (the boundary). The bound is the plan's `maxWaitLedgers`, an SDK option of 120 ledgers (about 10 minutes) by default; the CLI has no flag for it and uses the default. Beyond the bound the close is refused, as the matrix says: the plan is blocked with `SEQNUM_TOO_FAR`, and the CLI exits 3 without `--partial`.
- **X-10: what the ledger answers.** The matrix expects the sale to fail with `op_too_few_offers` or `op_under_dest_min`. Live, Horizon's strict-send path finder returned no record for the dust, so the planner never planned the sale and returned the dust to its issuer; a sale forced by hand failed with `op_under_dest_min` (edge case U4).
- **X-11: the fixture.** The matrix text had the account sell DUSTA. An own offer selling DUSTA sits on the other side of the book and is no liquidity for a sale of DUSTA for XLM; the row now names an own offer that sells XLM for DUSTA (the row above says why it was not built live).
- **M-01 and B-03.** The metric close ran on fresh messy fixtures (E3-S7). The builder's baseline fixture is kept for the recordings B-01 and B-02, and Dustin's close of the rebuilt baseline fixtures is B-03.
- **X-03, X-07, X-08: fixtures (E4-S3).** The matrix names a helper's claimable balance and an account FIX-J with four offer types that an MM fills. They are variants of the one `edge` profile (canonical decision 3): `claimant`, `offer-types` (the XLM-selling offer is its sell offer; plain sell offers are the messy fixture's) and `offer-stale`, a second account because the X-07 account closes in full. The counterparty that takes the stale offer is the plain issuer, with a strict-receive path payment: a buy offer would need a reserve for an offer that could rest (`op_low_reserve`, observed on 2026-09-28). The code Horizon returns is `op_offer_not_found`, not `op_not_found`.
- **X-03: warning, not blocker.** The plan stays closable and its hash does not change; the snapshot carries the balances outside its hash, since they are not the account's entries. The warning is in the plan the CLI prints before the confirmation, and the report repeats it.
- **X-07: evidence.** Horizon's effects of the close show no `trade` (the offers were cancelled, not filled) and `account_removed`; the test does not look for `offer_removed` effects.
