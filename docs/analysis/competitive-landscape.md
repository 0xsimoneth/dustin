# Dustin — Competitive Landscape: Account Closure and Cleanup Tooling on Stellar

Status: research memo for the Dustin Instaward (30 days, classic G accounts, testnet only). Written 2026-09-25 by the builder's analysis pass. All network figures and repository states are dated inline; sources are numbered `[S#]` and listed at the end, followed by the assumptions made.

## 1. Summary

1. **Every SOW claim about the incumbent is verified.** The StellarExpert Account Demolisher builds each intermediate transaction with the account being closed as source and fee payer, never uses fee-bump envelopes, has no sponsorship logic, offers no dry run, exposes no callable interface, and its closed-source server refuses to co-sign a merge whose payout is below 1 XLM (black-box probe on testnet, 2026-09-25: a 0.9999999 XLM payout was rejected, a 1 XLM payout was co-signed). MIT licence confirmed. Section 3 gives file-level evidence.
2. **The field is no longer empty; the SOW's "there is already a tool" is one SCF round out of date.** SCF #44 (recap published 2026-07-24, three days before the SOW date) ran an RFP titled **"Account Demolisher"** and funded **two** responses: **LumenWipe** (web app + hosted API + npm SDK, Apache-2.0) and **Account Demolisher** (web app at demolisher.app, Apache-2.0). Both run the classic wind-down on testnet and mainnet today and are actively developed (LumenWipe: 228 commits since 2026-05-12, last push 2026-09-23; Account Demolisher: 182 commits in the 90 days to 2026-09-21). Public records disagree on the award amounts: the SCF recap and both submission pages say "$120,000 worth of XLM" per project, the LumenLoop directory field `scf.awarded_total` records 36,000 for LumenWipe and 72,000 for Account Demolisher, and the Account Demolisher submission's own tranche list sums to $108,000; all three are reported side by side and none is treated as final (see Assumptions). [S10][S11][S12][S13][S26]
3. **LumenWipe is the direct overlap with Dustin's pitch.** Its API gained a CAP-15 fee-bump sponsor endpoint for reserve-locked accounts in PR 216 (merged 2026-09-08; the code is on `main` at commit `88ebff7`, 2026-09-23), it publishes `@lumenwipe/sdk` 0.2.0 on npm (2026-09-23), it has a plan endpoint, a per-asset disposal choice, a sponsorship-reconciliation module and 120+ unit test files. Two facts bound the overlap: the SDK "only talks to the LumenWipe API over HTTP — it builds no transactions itself and has no `@stellar/stellar-sdk` dependency", and the README's own roadmap still lists "sponsored fees for reserve-locked accounts" (Tranche 2) and the "public REST API and TypeScript SDK for integrators" (Tranche 3) as **Planned**, with Tranche 1 (classic MVP) **In progress**. Whether the hosted fee sponsor is switched on in production is not visible from outside. [S12][S13][S14][S36]
4. **The second awardee, Account Demolisher, rejects fee-bump envelopes** in its mediator and multisig code and is a `"private": true` Next.js app — no library, no CLI. It cannot close an account that has no spendable XLM. [S11][S15]
5. **Wallets do not offer an orchestrated close.** LOBSTR runs a separate custodial "Merge Tool" (secret key sent to LOBSTR, 0.1–0.9 XLM fee); xBull exposes the raw account-merge operation; XLMwallet's "merge" is a send-everything button; Freighter closed its merge request without a feature; Vibrant and Beans: nothing found in these sources. [S16]–[S20]
6. **First-party code has primitives, not orchestration.** `stellar-cli` offers `tx new account-merge`, `change-trust`, `manage-data`, `manage-sell-offer`, path payments and the three sponsorship operations, but no fee-bump wrapper (only `bump-sequence`). The TypeScript Wallet SDK exposes `accountMerge`, `removeAssetSupport`, `sponsoring`, `makeFeeBump`. `stellar/js-stellar-wallets#98` ("Add helper that closes a user's account") was opened 2019-08-12, has 0 comments, is still open, and the repository was archived 2024-02-08. So the precise statement is: **no first-party or backend-free programmatic closure interface exists; the only programmatic surfaces are LumenWipe's hosted, API-key-gated REST API with an HTTP client SDK, and an unfunded, unpublished planner-only SDK that cannot execute (item 8).** [S21]–[S24][S38]
7. **What remains open for Dustin (section 9)**: an in-process library and CLI that closes a **zero-spendable-XLM** classic account with every transaction fee-bumped by the **integrator's own** sponsor key — no hosted API, API key, co-signing server or mediator in the path; a **read-only planner** with a reason and fee estimate per step; explicit modelling of **sponsored trustlines** and the **`ACCOUNT_MERGE_SEQNUM_TOO_FAR`** guard; and a **published edge-case matrix plus a recorded baseline** of the incumbent stopping on the same fixture. None of the tools surveyed offers that combination; the closest, LumenWipe, offers sponsorship only through its hosted endpoint (0.1 XLM cap per transaction, API key required).
8. **A third, unfunded RFP response is the closest analogue to Dustin's D1 planner.** `@bleu/account-demolisher` (Apache-2.0, a single commit dated 2026-05-30, not published on npm, 0 stars) is a standalone TypeScript planner on `@stellar/stellar-sdk` with a mandatory dry-run preview, merge-precondition validation including the `SEQNUM_TOO_FAR` bound, a ≤100-op packer and a dry-run CLI whose header says it "NEVER signs or submits". It has no execution, no fee-bump and treats sponsorship only as a blocker, so it cannot close any account, let alone a zero-XLM one. A fourth repository created 2026-06-09 contains a README only. [S37][S38][S39]
9. **The hosted StellarExpert Demolisher is live as of 2026-09-25**, despite that June 2026 README claiming it "is no more": the route and the services-menu entry are in the explorer source at commit `308ef22` (2026-09-19), the testnet co-sign endpoint returned a signed envelope on 2026-09-25, and the public-network mediator received merges on 2026-09-23 and 2026-09-24. The bare HTML shell that the page URL returns without JavaScript is the normal response of a client-rendered app, not evidence of removal. [S1][S8][S9][S39]

## 2. Scope and method

- Question: who already closes or cleans up Stellar classic (G) accounts, where does each tool stop, and what is left for a 30-day, classic-only, testnet-only library?
- Sources in order of preference: primary source code (cloned at the commits stated), live network data (Horizon, StellarExpert API) [S3][S4][S9], the Raven MCP (LumenLoop directory and SCF submissions, Stellarlight/Scout repository index, official docs), the SCF #44 round recap, vendor documentation, and the LumenLoop (728 projects) and Electric Capital (9,027 repositories) datasets shipped in the project's skills folder [S29][S34].

- Items out of Dustin's scope by SOW (mainnet, C addresses, LP withdrawal, raised multisig thresholds, claimable balances, wallet UI) are noted where a competitor covers them, because reviewers will compare.

### 3.1 Is the hosted tool still live?

A README-only repository created 2026-06-09 states that the StellarExpert tool "at the time of creating this file is no more", and the page URL answers with only the explorer's HTML shell ("StellarExpert requires JavaScript turned on"), which is inconclusive on its own. Three independent checks settle it: (1) the current explorer source at commit `308ef22` (2026-09-19) still declares `<Route path="/demolisher/:network">` in `views/router.js` and lists "Account Demolisher" in the active `services` menu of `views/layout/top-menu-view.js` (a second, commented-out copy of the entry sits four lines below it); (2) the testnet co-sign endpoint `POST /demolisher/testnet/merge` returned an HTTP 200 co-signed envelope on 2026-09-25; (3) Horizon shows `account_merge` operations into the public-network mediator on 2026-09-23 and 2026-09-24 and a forwarding payment at 2026-09-25T00:23:59Z. The monthly merge counts never reached zero in 2026 (low of 18 in 2026-05), so if there was an outage in June 2026 it was short. Conclusion: live on both networks as of 2026-09-25; the June claim is not supported. [S1][S8][S9][S39]

## 4. The SCF #44 "Account Demolisher" RFP and its two awardees

The SCF #44 recap (2026-07-24) describes the RFP as "A production-ready tool to cleanly close a Stellar account — unwinding positions, removing trustlines and data entries, converting balances to XLM, and merging the account — across both classic and Soroban DeFi", lists two awards under it, and notes that 8 of 30 RFP-track submissions were awarded across 5 RFPs. Both submission pages on communityfund.stellar.org show status "Awarded" for round SCF #44. On amounts the public records disagree: the recap and both submission pages state "$120,000 worth of XLM" per project; the LumenLoop directory field `scf.awarded_total` shows 36,000 for LumenWipe and 72,000 for Account Demolisher; and the Account Demolisher submission's tranche list (24,000 + 36,000 + 48,000) sums to 108,000. The figures are given side by side and none is treated as final. [S10][S11][S13][S26] The full RFP text was not retrievable (the handbook page now lists Q3 2026 RFPs only; the April 2026 archived copy predates the Q2 list); the awardees' submissions reference "the RFP's temporary mediator" and "two protocols beyond the RFP minimum", so the RFP evidently specified a mediator for exchange destinations and a minimum set of DeFi exits. [S13][S35]

### 4.1 LumenWipe (lumenwipe.com, api.lumenwipe.com, `@lumenwipe/sdk`)

- Identity and activity: GitHub organisation repository created 2026-05-12, 228 commits on `main`, last push 2026-09-23, 3 stars, Apache-2.0; monorepo with Next.js web, NestJS API, a playground, `@lumenwipe/types` and `@lumenwipe/sdk`. CI workflows: `ci.yml`, `e2e-nightly.yml`, `publish-sdk.yml`, `deploy-api.yml`, `onchain-monitors.yml`. Directory lists it as based in Costa Rica. Submission: "responds to the Account Demolisher RFP … built by a two-time SCF Build Award team with a classic account wind-down already live on mainnet" (vendor statement). [S12][S13][S26][S36]
- Implemented today (source at `88ebff7`, README): deterministic ordered plan (normalize signers → data entries → claimables → offers → classic LP withdraw → DeFi exits → convert → trustlines → merge); IndexedDB session state machine with resume; browser-side `verify()` before signing; shared persistent mediator for exchange destinations with an exchange/memo registry; per-asset disposal decision `convert_to_xlm | return_to_issuer | transfer_to_account | acknowledged`; sponsorship modules that record the sponsor of every trustline, offer, data entry and signer and reconcile reserve counts; a `closePlan` endpoint and web plan view; 80 API and 43 web unit test files plus integration and e2e suites; a playground that seeds a messy testnet account (ephemeral assets `AIRDROP1`, `RUGPULL`, optional `USDC`/`EURC`). README status line: "the classic account wind-down runs today on testnet and mainnet. Soroban & DeFi protocol exits, the allowance inspector, and sponsored fees are in active development". [S12]
- Fee-bump sponsorship (verified): PR 216 "feat(api): sponsor the fee of a wind-down transaction for reserve-locked accounts" was merged 2026-09-08 into `feature/phase-2` (16 files, +804), implementing `POST /:network/fee-bump/sponsor`; the code is on `main` at `88ebff7`. The endpoint requires an API key; refuses fee-bump-of-fee-bump; requires the inner fee to be exactly `0`; allow-lists wind-down operation shapes only (`changeTrust` limit 0, offer cancels, `manageData` deletes, signer-normalising `setOptions`, `claimClaimableBalance`, `pathPaymentStrictSend`, `accountMerge`); requires every operation to act for the transaction source; caps the sponsored fee at `MAX_FEE_BUMP_STROOPS = 1_000_000` (0.1 XLM); returns 503 `fee_bump_not_configured` when `FEE_ACCOUNT_SECRET_*` is unset. The close builder detects reserve-locked accounts (`accountCanAffordFee`) and emits fee-0 transactions flagged for sponsorship. The README roadmap nevertheless lists sponsored fees under Tranche 2, "Planned". [S12][S36]
- **Zero-XLM account today**: possible in code, through the hosted API only, with a per-transaction cap of 0.1 XLM and an API key; whether the production deployment has a fee account configured is not visible from outside. [S12]
- Programmatic surface: `@lumenwipe/sdk` (0.1.0 on 2026-09-07, 0.2.0 on 2026-09-23) is "a typed fetch client for the LumenWipe API … it builds no transactions itself and has no `@stellar/stellar-sdk` dependency"; `runClose` drives fetch → verify → sign → submit loops against `https://api.lumenwipe.com` with an API key. The API is open source and self-hostable, but it is a NestJS service with a mediator co-sign key and a fee account, not a library. The submission states volume API/SDK usage "carries a small fee". README roadmap lists the "public REST API and TypeScript SDK for integrators" under Tranche 3, "Planned". [S12][S13][S14]
- Where it stops for Dustin's purposes: no in-process, backend-free use; `ACCOUNT_MERGE_SEQNUM_TOO_FAR` appears only as an error-message mapping ("Sequence number is too far ahead. Please retry."), not a guard; no CLI; no published edge-case matrix document or comparative baseline against the incumbent (tests exist in-repo). [S12]

### 4.2 Account Demolisher (demolisher.app)

- Identity and activity: Next.js web app, Apache-2.0, `"private": true` (not published to npm); repository linked from the SCF submission, cloned at commit `764d808` (2026-08-25); 182 commits in the 90 days to 2026-09-21; 1 star. Submission lists three tranches: MVP (audit layer, classic engine and mediator merge, wallet UI), testnet (Soroban tokens, DeFi exits, dry-run plan tree, multisig), mainnet (hardening, audit remediation, docs). [S11][S15][S27]
- Implemented (README, in-repo docs, source): four stages audit → plan (DAG of 13 node kinds) → simulate → execute; classic closure incl. offers, trustlines, data entries, extra signers/thresholds, optional claimable balances; Soroban DeFi exits (Blend, Aquarius, Soroswap, FxDAO); conversion via the Soroswap aggregator; un-routable assets left in place unless the user consents to return them to the issuer; CEX destinations through a per-closure throwaway mediator derived from a server-side `MEDIATOR_SECRET`; multisig signature collection via a relay; SEP-41 allowance viewer; typed last-four-character confirmation; contract allow-list; testnet/mainnet switch; signing via stellar-wallets-kit; unit, integration (live testnet closes) and e2e tests. [S15]
- **Zero-XLM account today: no.** Fee-bump envelopes are rejected — `src/lib/multisig/partial-xdr.ts` ("fee-bump envelopes are not supported here"), `src/lib/plan/simulator.ts` throws if a fee-bump is produced, and the submission says the mediator "rejects malformed and fee-bumped envelopes"; the closing account pays its own fees. [S11][S15]
- Sponsorship: `computeCoverableSponsorships` auto-revokes entries the account sponsors for itself and hard-blocks accounts that sponsor other accounts; the audit records `numSponsored` and a per-balance `sponsor`, but no plan node models a reserve returning to a foreign sponsor. No `ACCOUNT_MERGE_SEQNUM_TOO_FAR` handling found. No CLI, no library. [S15]

Verified from source at commit `aaae316`, the repository's only commit, dated 2026-05-30 (GitHub reports a push on 2026-09-10); Apache-2.0; 0 stars; workspace package `@bleu/account-demolisher` 0.1.0, not on npm (404 on 2026-09-25); sole dependency `@stellar/stellar-sdk` 15.1.0. ## 6. First-party CLI and SDK surface

- **stellar-cli** (`FULL_HELP_DOCS.md` at `main`, fetched 2026-09-25): `stellar tx new account-merge`, `change-trust`, `manage-data`, `manage-sell-offer`, `path-payment-strict-send/receive`, `begin-sponsoring-future-reserves`, `end-sponsoring-future-reserves`, `revoke-sponsorship` (with `--asset`, `--data-name`, `--offer-id`, `--liquidity-pool-id`, `--claimable-balance-id`, `--signer-key`), and `stellar tx operation add …` for multi-operation transactions. The only "bump" command is `bump-sequence`; nothing wraps a transaction in a fee-bump envelope, and ecosystem issues repeat that gap. [S21][S22]
- **TypeScript Wallet SDK**: helpers `createAccount`, `lockAccountMasterKey`, `addAccountSigner`, `removeAccountSigner`, `setThreshold`, `addAssetSupport`, `removeAssetSupport`, `swap`, `pathPay`, `setMemo`, `accountMerge`, `addOperation`, `sponsoring`, `makeFeeBump`. Primitives only. [S23]
- **js-stellar-sdk**: `Operation.accountMerge`, `Operation.changeTrust`, `TransactionBuilder.buildFeeBumpTransaction` — the blocks Dustin composes; no helper. npm searches (2026-09-25) for "stellar demolisher", "stellar account merge", "stellar close account" return `@lumenwipe/sdk` as the only closure-specific package. [S6]
- **js-stellar-wallets#98** "Add helper that closes a user's account": opened 2019-08-12 (two days after the Demolisher launch; the body quotes the Demolisher's feature list), 0 comments, open, repository archived 2024-02-08. [S24]
- Protocol facts Dustin relies on (official docs): an account "can only be merged once it holds no non-signer subentries: any trustlines, offers, or data entries must be removed first"; `ACCOUNT_MERGE_SEQNUM_TOO_FAR` = "Source account sequence number is too high"; a fee-bump's fee must be at least the network minimum for the inner operations plus one and the fee account must hold enough XLM; with sponsorship the minimum balance is `(2 + numSubEntries + numSponsoring − numSponsored) × baseReserve`, and "when a sponsored entry or subentry is removed, numSponsoring is decreased on the sponsoring account and numSponsored is decreased on the sponsored account" — the reserve returns to the sponsor. [S25][S32][S33]

## 9. Gap analysis and positioning relative to LumenWipe

- **No longer unique**: "closes messy accounts", "plan before signing", "disposes of leftovers", "sponsorship-aware", and even "fee-bump for reserve-locked accounts" each exist in at least one funded successor, and a backend-free planner with a dry-run CLI and a seqnum precondition exists as an unfunded, single-commit SDK. The write-up and README must say so, with links; reviewers will find it otherwise.
- **Relative to the unfunded bleu planner**: Dustin's D1 is conceptually the same artefact (pure plan over account state, preview, CLI). Dustin's contribution over it lies in D2 and D3 — actually executing the plan with every transaction fee-bumped, the automatic disposal ladder with stated reasons, sponsored-trustline unwinding rather than a blocker, the illiquid/auth-required/clawback cases, and the recorded baseline. The write-up should credit that repository as prior art for the planner and say this plainly.
- **Verifiable differentiators, stated against LumenWipe**:
  1. **Backend-free library with a read-only planner.** `planClose()` and `executeClose()` run inside the integrator's process on top of `@stellar/stellar-sdk`; no API key, hosted API, mediator account or co-signing server. LumenWipe's SDK is an HTTP client that "builds no transactions itself and has no `@stellar/stellar-sdk` dependency"; its API is a NestJS service holding a mediator key and a fee account. Verification: Dustin's `package.json` dependency graph and an offline planner test.
  2. **Fee-bumped zero-XLM close end to end, with the integrator's own sponsor key and no fee cap imposed by a third party.** LumenWipe's sponsorship is a hosted endpoint capped at 0.1 XLM per transaction, gated by an API key, and still "Planned" in its own roadmap; Account Demolisher rejects fee-bump envelopes; StellarExpert refuses payouts under 1 XLM. Verification: the SOW success metric — a public testnet transaction chain closing a fixture with zero spendable XLM, every transaction a fee-bump envelope.
  3. **Sponsored-trustline unwinding, the seqnum guard, a published edge-case matrix and a recorded baseline.** LumenWipe records sponsors and reconciles reserves but publishes no matrix and no comparison against the incumbent; Account Demolisher blocks foreign sponsorship; neither guards `ACCOUNT_MERGE_SEQNUM_TOO_FAR`. Verification: the test matrix in the repository and the baseline recording in the evidence package.
  A fourth, smaller one: a CLI, which none of the three tools has and which stellar-cli cannot substitute for because it has no fee-bump wrapper.
- **Where to align rather than compete**: both awardees need exactly what Dustin produces — a small, auditable classic wind-down engine. Keeping Dustin's core as pure functions over `@stellar/stellar-sdk` types preserves an upstream path to either project, to the Wallet SDK (issue #98) or to stellar-cli.
- **Baseline recording**: Dustin's fixture should reproduce the StellarExpert fixture builder's shape (issuer assets, offers, data entries) but with zero spendable XLM, and the recording should show both the `txINSUFFICIENT_BALANCE` on the first cleanup transaction and, on a variant that frees under 1 XLM, the HTTP 400 from the co-sign endpoint.

## Assumptions

1. The StellarExpert co-sign rule "< 1 XLM refused" is inferred from four black-box responses on testnet on 2026-09-25 (0.5 and 0.9999999 XLM rejected; 1 and 5 XLM co-signed). The server code is not public; the precise rule, and whether mainnet differs, is assumed to match this behaviour.
2. The full text of the SCF "Account Demolisher" RFP could not be retrieved; its one-sentence description comes from the SCF #44 recap, and any further requirement is inferred only from the awardees' submissions. No claim is made about what the RFP required beyond that.
3. Award amounts: three public figures disagree (SCF recap and submission pages: "$120,000 worth of XLM" each; LumenLoop `scf.awarded_total`: 36,000 for LumenWipe and 72,000 for Account Demolisher; the Account Demolisher submission's tranche list: 108,000). They are reported side by side; the difference may be tranches paid to date or a data-entry artefact, and none is treated as final.
4. "Programmatic API" is judged on whether a third party can invoke the closure logic from code without a browser. A hosted REST API with an npm HTTP client counts as "yes (hosted)"; a private web app counts as "no"; an in-process library counts as "yes (backend-free)".
5. Competitor feature claims taken from READMEs, in-repo docs and SCF submissions are vendor statements; only items marked "verified" or "from source" were read in code. Repository states are as of the commit hashes given and may have moved after 2026-09-25. Whether LumenWipe's production API has a fee account configured is unknown.
6. Third-party URLs are reproduced verbatim in the Sources section even where a URL contains the publisher's account handle (GitHub organisation or Medium handle), because traceability of every claim takes precedence. No individual is named in the body; repositories owned by personal accounts of minor, dormant projects are cited through the dataset or query that surfaced them rather than by URL.
7. Wallet coverage is limited to LOBSTR, Freighter, xBull, XLMwallet, Vibrant and Beans plus the Scout wallet roster; "no close-account feature found in these sources" is not evidence that no such feature exists.
8. Mediator usage counts (58,388 payments; 1,116 merges in 13.7 months) assume one forwarding payment per closure and that all `account_merge` operations into the mediator originate from the Demolisher flow.
9. The Dustin row in the landscape table describes the SOW's committed deliverables, not shipped software; "Yes" entries there are targets that the evidence package must demonstrate.
