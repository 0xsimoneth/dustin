# Independent pre-release review of 0.1.0 (2026-09-29)

An independent review of `stellar-dustin` 0.1.0 as prepared for its first npm publish, done by a reviewer who followed only the README and the documents it links, as a newcomer would. Nothing in the product was changed; this file is the only output.

## Scope

- A fresh public clone of `https://github.com/0xsimoneth/dustin.git` into `<clone>`, at `e865bec9e052842cb6791d24e0d8215c680be5e5` (origin's `main` at 07:54 UTC, "Release prep: CHANGELOG 0.1.0 and the version fields at 0.1.0"). While the review ran, `main` moved to `64789be`, a documentation-only commit (`docs/README.md`, `docs/prd.md`, two analysis documents); nothing below depends on it.
- CI on the reviewed commit: the public run list shows the CI workflow green on `e865bec` (run 36539346346, 07:53 UTC).
- Machine: macOS (Darwin 25.6.0), Node.js v24.15.0 and npm 11.12.1; Node.js v22.14.0 for the engines check. Other processes were loading the machine during the review, so the durations below are upper bounds.

## Method

1. Fresh clone to green, from the README alone: the six commands of step 1, each timed with wall-clock UTC timestamps; then the same on a second fresh clone with an empty npm cache (`npm ci --cache <tmp>/emptycache`) to approximate a fresh machine; then the offline tier on Node 22.14.0; then the live tier exactly as the README writes it.
2. The testnet flow from the README and from `docs/demo-video-script.md`, on five throwaway `messy` fixtures built with `dustin fixture create` (A to E). `dustin` was put on the PATH with the demo script's `npm link`, pointed at a scratch prefix (`npm_config_prefix=<tmp>/prefix`) so the machine's global npm prefix was not touched. With no terminal attached, the typed confirmation and the hidden secret prompt were driven through a pseudo-terminal (`script -q <file> dustin ...`, input fed after the question appeared). Secrets were exported from each fixture's `keys.json` inside the same script, never echoed; every output file was counted for seed-shaped strings before it was read.
3. The package: `npm pack --dry-run`, `npm run check:package`, `npm pack` into a temp directory, `npm install <tarball>` in an empty project `<tmp>/app`, the README's SDK snippet (planClose only) in ESM and CommonJS, and `tsc --noEmit` on the whole snippet.
4. Security: code reading of every secret, network, exit-code and report path; the mainnet refusal against a local stub on 127.0.0.1 that answers Horizon's root with `Public Global Stellar Network ; September 2015` (`DUSTIN_HORIZON_URL=http://127.0.0.1:<port>`), with every request it received logged; secrets on argv, in the environment and in `.env`; `--report` refusals; the CI workflows; the dependency tree and `npm audit`; a seed scan of the tracked tree and of every blob in the history (names and ids only).
5. Documents against the code: 21 concrete claims from the README, the integration notes, the write-up and the evidence package, each checked against the source or the committed evidence; `npm run evidence:check`.

No mainnet service was contacted. The baseline fixture `messy-20260926T035942Z` and the main repository's `.fixture/` were not read or touched.

### D-1 (minor): the README's testnet flow does not say how to supply the two secrets

- Where: `README.md:56` (the secret sources), `README.md:179-187` (the fixture by hand, ending "`dustin plan` and `dustin close` then run on that account like on any other").
- Evidence: following the README, `dustin fixture create` prints the account, destination and sponsor and says the keys are in `.fixture/<id>/keys.json`; `close --execute` then exits 2 with `MISSING_ACCOUNT_SECRET` (step 2 #5). Nothing in the README says that the fixture's own fee sponsor (funded from Friendbot) is the account to use for `DUSTIN_SPONSOR_SECRET`, nor that the two values are `secrets.fixture` and `secrets.sponsor` in `keys.json`; only the demo script's step 4 (`docs/demo-video-script.md:58-62`) does, and a reader has to open it and guess that it applies.
- Fix: add the demo script's `.env` one-liner (or an `export ... $(node -p ...)` form that prints nothing) and one sentence naming `secrets.fixture` and `secrets.sponsor` under "A fixture by hand".

### D-2 (minor): the published README would say "not yet on npm"

- Where: `README.md:9` ("Status: 0.1.0 prepared, not yet on npm ... until then, install from source"), `README.md:37-42` ("From npm, once 0.1.0 is published (pending, the builder's action)"), `README.md:81`, `README.md:218`; `package.json` `files` and npm's rules always pack `README.md`.
- Evidence: `tar -tzf stellar-dustin-0.1.0.tgz` lists `package/README.md`, 21,651 bytes, identical to the repository's; npmjs.com renders the README of the published version, so a `npm publish` of `e865bec` shows "not yet on npm" on the package's own page until 0.1.1.
- Fix: update the README's status, install and Status-table lines in the commit that is published (then tag it), rather than after the publish.

### D-3 (minor): the Horizon root check is the one request without a retry

- Where: `src/config/network.ts:99-146` (`verifyHorizonIsTestnet`, one `fetch` with a 15 s timeout, line 124) against `src/reader/horizon-json.ts:34-44` (three retries with backoff).
- Evidence: at 08:27 UTC, with the live tier running, `dustin plan GB6LHM... --to GAGAQY...` exited 6 with `HORIZON_UNAVAILABLE: Horizon at https://horizon-testnet.stellar.org is unreachable.`; the same command a minute later (08:27:34) exited 0. Every command's first request is this check, so one dropped connection, on a network that drops as this one does, ends `plan`, `close`, `fixture create`, `fixture verify` and `executeClose` before any retry logic runs.
- Fix: give `verifyHorizonIsTestnet` the read client's retry policy for network errors, 429 and 5xx (it is before any submission, so a retry is always safe).

### D-4 (nit): fixture command failures exit 1, "unexpected error"

- Where: `src/cli/exit-codes.ts:36-64` (the `default` branch), `docs/errors.md:48,51`, `README.md:137`.
- Evidence: `dustin fixture verify /nonexistent/manifest.json` and `dustin fixture verify package.json` both exit 1 (`MANIFEST_INVALID`); `FRIENDBOT_FAILED` before any submission also maps to 1. `docs/errors.md` documents these, but the README's table defines 1 as "Unexpected error" and 2 as "Usage or validation error", so a script cannot tell a mistyped path from a bug, and a Friendbot outage from a crash.
